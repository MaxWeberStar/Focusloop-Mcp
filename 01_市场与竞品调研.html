一、研究问题

FocusLoop 试图解决的问题不是模型底层的 Transformer 注意力，而是 AI Agent 在长任务中出现的目标漂移、范围膨胀、上下文失控和关键决策遗忘。

核心假设：如果把用户目标、成功标准、任务树、关键决策和检查点外置为可查询状态，并在高风险偏移时请求用户确认，Agent 的长任务可靠性可以提升。

二、市场纵向观察

阶段 1：从聊天记录到项目上下文

早期 AI 产品主要依赖当前对话窗口。用户需要反复补充背景，Agent 的“记忆”更多是上下文长度带来的暂时保留。

随后出现了项目级上下文：Claude Projects 将文件、指令、知识库和项目内对话组织到一个工作空间中；Cursor Projects 则进一步引入协调 Agent、并行任务和长期项目上下文。它们解决了“每次从零解释”的问题，却不等同于目标治理：知道更多上下文，不代表知道当前应该做什么。

阶段 2：从上下文保留到 Agent 记忆

Letta 将 Agent 定义为有状态系统，强调持续学习与长期记忆；Claude 也提供了面向 Agent 的 memory tool，用文件操作保存和检索跨会话信息。

这一阶段的重点是“记住事实、偏好和历史”，但记忆系统通常回答的是“过去发生过什么”，不一定回答“当前行动是否仍然服务于原始目标”。

阶段 3：从自主执行到可验证执行

Cursor Background Agents 可以异步执行任务、编辑代码、运行测试，并附带日志、截图和视频等交付证据；Checkpoint 机制允许恢复 Agent 之前的代码状态。

这说明市场正在从“让 Agent 自动完成”转向“让用户能够检查 Agent 做了什么”。但代码状态回滚解决的是结果错误，不能完全解决路线错误：Agent 可能沿着错误目标连续执行很多正确的局部动作。

阶段 4：目标漂移成为独立问题

近期研究开始把 goal drift / objective drift 作为独立问题研究：Agent 可能随着交互轮次增加，逐渐偏离最初目标，而且偏移可以是渐进、局部、难以察觉的。相关研究还观察到，长上下文会增加模式匹配行为与目标漂移之间的关联。

由此，FocusLoop 的市场切口是成立的：现有产品已经覆盖上下文、记忆、执行和回滚，但“目标—行动—决策—确认”的中间控制层仍然相对空缺。

四、重点竞品分析

Claude Projects：上下文容器

Claude Projects 的优势是把文件、指令、知识库与项目记忆放到同一工作空间，适合持续性研究和创作。它的产品逻辑是“给 Agent 一个稳定的背景”。

它的局限在于：项目上下文可以越来越丰富，却不自动区分当前主目标、次要探索和已被否决的方向。FocusLoop 可以把 Project 中的自然语言背景进一步压缩为目标契约（Goal Contract）。

Cursor Projects / Background Agents：执行协调器

Cursor 已经具备协调 Agent、并行 Agent、异步执行、测试和交付证据。它的长处是工程执行能力强，能把一个任务拆成多个代码任务并持续运行。

它暴露出的机会是：协调器负责分派任务，但用户仍需要判断分派是否改变了原始产品目标。FocusLoop 不需要和 Cursor 竞争代码执行，可以作为上层的“产品目标守门员”和“决策审计器”。

Letta：状态化 Agent

Letta 的核心优势是把 Agent 从一次性对话变为有状态、可持续学习的系统。它适合构建个人助手、编码 Agent 和嵌入式智能体。

FocusLoop 可以借鉴其状态化思想，但不直接复制长期记忆产品。FocusLoop 要保存的重点不是所有历史，而是少量高价值状态：当前目标、约束、决策、假设、未决问题和路线变化。

普通项目管理工具：结构清晰但不理解语义

Linear、Notion、Trello 等工具拥有成熟的任务、状态和协作机制，却要求用户自己维护任务结构。它们能记录“任务是否完成”，不能稳定判断“这个任务是否仍然服务于项目目标”。

FocusLoop 的差异化不在于再做一个看板，而在于让 Agent 自动生成、解释和维护任务结构，并把偏移判断呈现给用户确认。

五、竞品共性空白

目前市场能力大致分布在四个层面：

上下文：我知道哪些背景？
记忆：我记得过去发生了什么？
执行：我现在能做哪些动作？
回滚：出错后我能否恢复？

FocusLoop 提出的第五层是：

目标控制：我现在做的事情，是否仍然服务于用户真正想要的结果？

这不是替代上下文、记忆或执行系统，而是把它们连接起来的控制层。

六、FocusLoop 的定位建议

推荐定位

FocusLoop 是面向 AI Agent 长任务的目标锚定与路线纠偏层，在 Agent 行动前后维护目标契约、任务树和关键决策，并在发现高风险偏移时请求用户确认。

不建议的定位

  • 不要宣称“控制大模型底层注意力”
  • 不要一开始做通用项目管理平台
  • 不要把核心卖点写成“AI 更聪明”
  • 不要只做自动总结或聊天记忆

七、MVP 竞争策略

核心用户

第一批用户应选择正在用 AI 完成复杂任务的人：

  • AI 编程用户
  • 研究与写作用户
  • 独立开发者
  • 黑客松参赛者
  • 使用多个 Agent 协同工作的团队

MVP 四个能力

  1. 目标契约：提取最终目标、成功标准、非目标、限制条件。
  2. 任务树：将每次行动绑定到主任务或子任务。
  3. 偏移检查：判断当前行动是否改变目标、扩大范围、绕过约束或长期没有产出。
  4. 检查点回顾：输出已完成、路线变化、未决问题和需要用户确认的事项。

最小可演示流程

用户：我要做一个知乎黑客松项目
→ FocusLoop：提取目标契约
→ 用户：顺便做一个完整商业化后台
→ FocusLoop：识别为可能的范围膨胀，询问纳入、延后或放弃
→ 用户：先延后
→ FocusLoop：记录决策并恢复 MVP 路线
→ 阶段结束：输出路线回顾和下一步

八、横纵交汇判断

市场演进的方向不是简单地让 Agent 拥有更多记忆和更长运行时间。随着 Agent 越来越能自主执行，用户越来越需要知道它是否仍在解决原来的问题。

已有产品的历史路径决定了它们各自的强项：Project 产品从上下文出发，Memory 产品从持久状态出发，Coding Agent 从执行出发，项目管理工具从人工结构出发。FocusLoop 的机会来自这些路径交汇之后的缺口：目标一致性没有成为一个独立、可解释、可干预的产品对象。

最可能的竞争形态是：FocusLoop 不作为一个孤立聊天工具生存，而是成为 Claude、Cursor、Codex、开源 Agent 框架或自建工作流的控制层。

最危险的失败形态是：产品退化成“每隔几轮让 AI 总结一次”，用户感知不到它比普通总结 Prompt 好在哪里。

最乐观的形态是：FocusLoop 建立一套通用的目标契约和路线检查协议，任何 Agent 都可以通过 Skill 或 MCP 接入，并且能对“目标漂移”提供可解释证据。

九、下一轮研究问题

  1. 用户实际遭遇的路线失控，最常发生在编程、研究、写作还是多 Agent 协作？
  2. 用户愿意接受多高频率的主动打断？
  3. 什么样的证据足以让用户相信“发生了路线偏移”？
  4. 目标契约应该由 AI 自动生成，还是必须由用户显式确认？
  5. FocusLoop 先做 Codex / Claude Code / Cursor 中的哪一个载体，才能最快获得真实反馈？

十、阶段性结论

FocusLoop 具备真实需求基础，但竞争点不能停留在“帮 AI 保持专注”。它需要被做成一个可观察的控制循环：

目标定义 → 行动绑定 → 偏移检测 → 用户确认 → 决策记录 → 阶段回顾

建议下一步直接进入“用户场景访谈 + 失控案例采集”，同时制作一个不依赖复杂后端的 Skill 原型，用真实开发任务验证偏移检测是否比普通项目总结更有价值。

方法论说明

本报告采用横纵分析法：纵向追踪产品与问题从上下文、记忆到 Agent 执行的演进，横向比较当前市场中的项目、记忆、执行、回滚与项目管理产品，最后交叉判断 FocusLoop 的切入位置。
